## Scientific inference

The immediate ecological bottleneck is not just enough stored world energy or an inability of the native `DrawCompute` instruction to succeed: **a runnable process must arrive at a resource-requesting opcode while credit and pool are available**, without trapping during a temporary shortage. The current stochastic code almost never maintains this timing. VM-provided pool-paid access fixes a particular instruction-boundary condition only, but cannot rescue a zero-credit process parked at unrelated CIL instructions or reverse a fatal transient trap. The promising non-scripted feedback+resource witnesses are rare, finite, start from externally loaded code and I/O/register ports, and are not proof of autonomous self-maintenance.

**Next decision:** before changing policy, define an opt-in generic *nonfatal* resource request failure as a separately calibrated VM law and preregister a fresh matched random-genome prospective trial against the unchanged legacy kernel and the existing pool-paid policy. Negative controls must include no world pool, Draw-ablated source, and explicit event-level `pool_paid_attempt` provenance. A positive continuation would remain **environment-engineered resource accessibility**, not an internally invented cyberlife repair mechanism.
