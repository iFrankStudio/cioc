# CIOC V0.3 — 无完整模板的维护算法再生基准

本项目延续 CIOC V0.2，但不从源组件备份中恢复目标算法：目标程序在损伤后被清除，维护者只能枚举有限指令集中的候选程序，针对公开的任务行为样本进行测试，并经过独立保留输入集的验收后提交新程序。

## 运行

要求 Python 3.10+，无第三方依赖：

```bash
python run.py
python -m unittest -v
```

结果存入 `results/experiments.json`，包含逐次候选检查和提交日志。

## 世界设计

* 三个组织组件 A、B、C，维护许可关系：A→B，B→C，C→A。
* 组件功能为整数输入到整数输出的确定性转换：A(x)=x+2，B(x)=2x+1，C(x)=x²−1。**函数规范不是目标程序备份**，但它们提供了人工指定的正确性标准。
* 基础指令：`INC`, `DEC`, `DOUBLE`, `SQUARE`, `NEG`, `ADD3`；最多合成三条指令；执行绝对值上限 1,000,000。
* 训练输入 `(-2,-1,0,1,2)`，保留输入 `(-7,-4,3,5,8)`。搜索器仅枚举候选，无模板索引或生成式语言模型。
* 每次候选检查消耗 1 单位计算预算，最终提交消耗 3 单位。世界运行时检验权限和行为，但不提出候选。
* 正常初始组织程序故意不是最短实现；恢复出的 B、C 使用了与创世程序不同的代码。
* `GENESIS` 只用于初始化和显式外部恢复对照，内部搜索器不调用它。研究者和运行时仍知道任务规范；这不是未知任务的发现。

## 实验场景

`chain_regeneration`：依次损坏 B、C，观察是否能够内部合成并恢复。

`no_search`：搜索禁用；`external_baseline`：外部服务恢复；`disable_source`：禁用 A，阻断 B 的内部维护来源；`low_budget`：资源不足；`missing_primitive`：去除 `SQUARE`，使 C 的二次函数在现有有限候选程序下不可表示；`destroyed_search`：搜索器损坏且缺少自我再生机制；`recover_A`：C 恢复 A。

## 不应得出的结论

1. 本实验没有证明数字生命存在；仅验证有限任务上的内部程序再合成与对照。
2. 搜索器自身是固定的引导机制，尚未实现调节器的组织闭合。
3. 行为规范、指令集、搜索顺序、许可关系和预算是预置的，系统没有自主形成新目标。
4. 训练集与保留集都是有限的。程序通过测试不代表对所有整数都等价，也不代表已经实现开放式演化。
5. 此项目不能作为 CIOC 数学判据的充分验证：必须另行测量因果维护关系、组织边界和长期资源可行性。
