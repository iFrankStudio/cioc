# CIOC V0.6 — 互补维护组织、程序合成与功能契约修复

本项目是一个**可复现实验基准**，不是生命证明，也不是前一版 V0.5 的完全兼容升级。

## 运行

需要 Python 3.10+，不需要第三方依赖：

```bash
cd cioc_v06
python -m unittest -v
python run.py
```

运行后查看 `results/experiments.json`、`test_output.txt`、`summary.txt`。

## 新设计

- O（Observer）：监测任务程序与功能契约是否缺失，并发送维修请求；持有契约的一份片段。
- G（Generator）：从基础指令 `INC / DOUBLE / SQUARE / DEC` 组合长度 1～3 的候选程序。**没有完整目标程序备份**。
- V（Verifier）：使用功能契约执行候选程序，提供通过/失败反馈；持有契约的另一份片段。
- M（Modifier）：根据通过验证的候选提交新任务程序；将 O、V 提供的两个契约片段重新组装，并通过摘要校验。
- Task：可受损任务程序。正常目标为 `f(x)=2x+1`。
- Contract：可受损数据资产，以四个输入/输出样例表示功能要求。

O/G/V/M 角色不可互换，也不保存完整的通用维修代理。角色缺失即可能阻断修复链。任务程序由指令枚举重新合成；契约通过两份可恢复片段重建，**这属于数据恢复，不是从零推导功能目标**。

## 实验机制

- 预算：候选生成每次 1 计量单位，验证每次按样本数扣除预算，提交 2 单位，契约组装 3 单位。
- 世界驱动：只按固定次序调用正常角色并传递消息，不直接在 `tick` 中执行修复。
- 验证：合成程序必须通过训练契约的 4 个样例；另在 7 个未参与生成与提交的整数上检查泛化。
- 双片段：契约信息由一个确定性 XOR 掩码拆分为两份，需双方片段才能重建；附加摘要来自原契约，存储在 M 中。
- 内外干预：明确区分内部提交事件和 `restore_external()` 事件。
- 可控失败：禁用角色、缺少必要指令、预算不足、任一契约片段丢失、篡改片段等。

## 重要局限

1. **与 V0.5 的比较属于不同实验轴**：V0.5 的生命内部维护由可变图程序控制；V0.6 的 O/G/V/M 角色逻辑由宿主 Python 方法实现，仍属硬编码的角色策略，而非可修改的 CIL 算法图。V0.6 在“维护机制自身可修改”这一维度暂时退步，不应宣称全方位升级。
2. 世界内核仍包含 `evaluate` 解释器、消息队列、逻辑调度与资源管理；行为角色也是宿主 Python 方法。无法声称全控制流内生或完整组织闭合。
3. 契约修复通过冗余编码恢复既有信息，并非创造新验证规则；摘要也仍有中心化依赖。
4. 功能评估仅是小规模确定性整数函数，不能推断一般化程序合成能力。
5. 局部任务恢复不代表整个系统具备自生能力；O/G/V/M 自身不能再生，联合损伤导致失败是模型设计预期。
6. 此项目的 `target_fn` 仅用于**实验者独立留出验证**，正常内部搜索/验证/提交不会读取它。

## 后续可研究问题

- 将角色策略编译成可损坏、可替换的 CIL 图程序，统一 V0.5 与 V0.6 的能力。
- 将修复任务自身以及验证样例的更新机制纳入可追踪组织历史。
- 引入任务函数变化、外部扰动和多组件联合干预，估计维护超图与资源可行性。
- 使用多个独立随机种子、不同函数族及真正未见样本，测试可识别性与鲁棒性。
