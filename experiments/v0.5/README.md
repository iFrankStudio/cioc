# CIOC V0.5 — 由可变算法图驱动的维护决策

## 定位

该项目是用于检验组织维护机制的**有限概念验证**，不构成数字生命存在的证明。本版相较 V0.4 的主要改变：**不再存在宿主调用 `regenerate(target)` 的高级维修调度器**。宿主 `VM.run()` 只按轮次执行当前完好的图程序；损伤发现、候选枚举、结果判断及写回是图程序的指令与控制流。

## 运行

要求 Python 3.10+，仅使用标准库。

```bash
python run.py
python -m unittest -v
```

运行后 `results/experiments.json` 包含完整事件流水（含每个执行的节点、安装对象、预算变化）。

## 文件

- `cioc.py`：世界状态、有限图语法、受限解释器、隔离探针与资源配额。
- `run.py`：十个场景的执行入口。
- `test_cioc.py`：17 项边界与回归测试。
- `results/experiments.json`：实际执行输出。
- `test_output.txt`：测试输出。
- `实验报告.md`：设计、对照、结果、局限。

## 核心机制

1. A、B、C 的维护策略均存储为可删除、可替换的 `Graph`。删除一个图程序等于移除该节点的可执行维护能力。
2. VM 的基础指令集为 `READ`, `FIRST`, `IF_NONE`, `ZERO`, `DECODE`, `EVAL`, `IF_VALID`, `INC`, `IF_MORE`, `PUT`, `HALT`。
3. 活跃图程序先 `READ` 获得损伤列表、`FIRST` 选取目标；随后通过计数器和 `DECODE` 枚举候选图，由 `EVAL` 在隔离模拟环境中运行候选的行为测试，最后由 `PUT` 原子安装通过的候选图。
4. 目标原有源码不用于再生；新程序由有限的 4 比特图语法生成。该语法只有 16 个候选，**不是开放式程序合成**。
5. 只有基础 VM 调度、操作语义、图译码器、隔离执行机制、测试契约、权限与配额不可修改。该边界是实验的明确前提。

## 可信度与局限

- `READ`、`EVAL` 和 `PUT` 仍由宿主提供。`EVAL` 是固定的外部**验证能力**，不过维修目标、搜索流程和安装判断由个体图程序执行。不能说“所有调节过程完全内生”。
- 隔离验证使用一个**人造有限功能契约**：候选图必须能通过枚举找到可修复目标的图编码，并提交它。其 probe oracle 规定编码 15 才通过，目的是测试控制流行为，不是学习一般化的语义理解，也不是独立留出集证明。
- `viable()` 仅检验每个控制器是否具有这个玩具语法中有效的基因编码，不能充当生命指标。
- A、B、C 初始都是等功能控制器，因此成功主要体现受限的**冗余组织恢复**；尚未证明无冗余情况下的深层组织闭合或边界自发形成。
- 损伤只模拟删去完整图程序；没有细粒度数据污染、持续环境变化或复杂并发。
- 不能从 17 个测试通过推断通用安全性、生命性或无限期可行性。
