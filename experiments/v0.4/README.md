# CIOC V0.4：可变调节组件的再生与联合损伤实验

这是对 CIOC V0.3 的增量概念验证（toy benchmark），**不是发现、证明或创造数字生命的证据**。

## 目的

把维护过程中的三类角色也作为可受损的、可重构的程序资产：

- `S`：候选搜索控制程序（search）
- `V`：功能验证控制程序（verify）
- `M`：原子提交控制程序（commit）

为了测试局部损伤后的恢复，每个节点带有一个**可损坏的次要能力程序**：`S` 还携带 commit，`V` 还携带 search，`M` 还携带 verify。这不是隐藏的外部修复器，而是模拟个体内预先存在的冗余程序资产。它也意味着本实验的组织边界依赖这种初始设计。

## 环境要求

Python 3.10+，标准库，无第三方依赖。

```sh
python run.py
python -m unittest -v
```

运行结果写入 `results/experiments.json`、`results/console.txt`，测试输出见 `results/tests.txt`。

## 文件说明

- `cioc.py`：受限指令集、可变组件、资源计量、有限候选生成及事务安装
- `run.py`：全部场景，生成带事件历史的 JSON
- `test_cioc.py`：行为回归与边界测试
- `实验报告.md`：研究问题、运行结果、限制和后续方向

## 重要限制与可信度边界

1. 世界运行时**仍然固定提供**：指令解释语义、目标功能契约、资源计量、权限判断、事务语义与 `regenerate()` 的调度。候选遍历循环虽然只有活跃的 resident search 程序才会触发，但其 Python 实现本身并未成为可损坏的组织组件。
2. 所谓“算法合成”是从有限 `TOKENS` 中枚举长度不超过 3 的组合，并寻找满足已知功能契约的程序；不是开放式程序发明。
3. search/verify/commit 的功能契约是对必要原语的包含性验证，**不是对复杂算法语义的普遍测试**。训练与留出探针虽被分别执行，但当前契约与输入值无关，因此无法构成独立泛化证据。
4. 每次修复由**实验调度器显式调用**，没有自发发现故障、调度修复的独立目标形成机制。
5. 模型尚未检验复杂联合维护的高阶因果作用、无限期资源可行性、组件分割粒度不变性，也未实现自我组织边界发现。
6. 因此不能把结果解释为“验证了完全组织闭合”或“证明赛博生命存在”。

## 下一步
