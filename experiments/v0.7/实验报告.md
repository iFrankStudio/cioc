# CIOC V0.7 实验报告：互补维护角色的局部程序再生

## 研究问题

在生成器 G 的可执行程序已丢失、没有可直接执行的完整 G 备份时，剩余角色能否协作构造并安装程序？该结果能否与外部修复、资源不足和片段缺失区分？

## 实验方法

模拟四个角色：O 观测、G 生成、V 验证、M 提交。角色程序本身为可删除和安装的指令序列。O 持有各目标程序第一条指令的提示，V 持有第二条指令提示，缺少完整副本。宿主提供受限枚举、角色执行、固定契约检查与原子安装原语；具体执行路径由存活角色的指令控制。

## 实际结果

| 场景 | 是否恢复 | 内部安装 | 检查候选 |
|---|---|---:|---:|
| 损坏 O | 否 | 0 | 0 |
| 损坏 G | 是 | 1 | 32 |
| 损坏 V | 否 | 0 | 81 |
| 损坏 M | 否 | 0 | 47 |
| 联合损坏 G、M | 否 | 0 | — |
| 预算不足 | 否 | 0 | — |
| 缺失 V 的 G 片段 | 否 | 0 | — |
| 外部恢复 G | 是（外部） | 0 | — |

本地原始 V0.7 运行：`python -m unittest -v`，12/12 通过；`python run.py` 退出码 0。对应原始运行结果见 `outcomes.json`。

## 结论与局限

G 单独损坏后，剩余角色能在有限搜索下协作恢复 G 的程序，并与外部恢复区分；但 O、V、M 仍为单点故障。当前契约是精确 opcode 序列匹配，不是独立的行为泛化验证。宿主提供枚举和安装原语，且恢复能力部分来自 O 的备用枚举路径。这只能支持“有限互补程序恢复”，不能证明完整组织闭合、开放式演化或数字生命。

## 复现与版本注意

GitHub `main` 已恢复本地原始 V0.7 的 `cioc.py`、`test_cioc.py` 和 `run.py`。这些文件的 Git blob SHA 已与本地 `git hash-object` 核对一致，`outcomes.json` 也与本地归档一致。原始测试在本地重跑 12/12 通过，八个场景与 `outcomes.json` 一致。GitHub Actions 的远程执行状态另行核对；本地通过不等于远程 CI 已通过。
