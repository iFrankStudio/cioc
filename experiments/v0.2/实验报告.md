# CIOC V0.2：维护机制再生实验报告

版本：0.2；研究定位：小规模确定性合成基准；实验环境：Python 标准库。

## 研究问题

当系统中的**维护算法自身**失效时，是否能够由组织内部其他功能组件重建？系统能否避免把外部修复当作内部维护？受资源和备份可靠性限制时会怎样？

## 方法

三个组件 A、B、C 形成环式修复权限，分别持有下一组件的备份与指令片段。损坏目标的可执行程序；驻留策略在权限与预算范围内枚举三个基础操作（LOAD、WRITE、VERIFY）的不同排列，世界执行器在隔离语义下验算候选修复程序，合格才提交。每次候选尝试耗费 2 单位预算。实验包含固定策略、外部修复、维护源禁用、低预算和坏备份对照。

注意：采用固定规范程序（LOAD→WRITE→VERIFY），这些实验**不是**无先验条件下的开放式算法发现。

## 实测结果

| 场景 | 核心可用 | 内部提交 | 外部修复 | 候选检验 | 剩余预算 |
| --- | --- | ---: | ---: | ---: | ---: |
| 内部再生（两次连续损伤） | 是 | 2 | 0 | 8 | 84 |
| 禁止自修改 | 否 | 0 | 0 | 0 | 100 |
| 外部修复 | 是 | 0 | 1 | 0 | 95 |
| 禁用维护源 A | 否 | 0 | 0 | 0 | 100 |
| 预算不足（初始 3） | 否 | 0 | 0 | 1 | 1 |
| 内部备份损坏 | 否 | 0 | 0 | 6 | 88 |

`python -m unittest discover -v`：11/11 通过。结果来自确定性模拟，可在标准库环境下重现；没有随机置信区间可报告。

## 解释

内部再生条件下，A 首先恢复 B，恢复后的 B 再恢复 C；在当前仿真定义下，确实存在维护机制之间的内部功能依赖。禁用唯一维护源、移除结构可塑性、减少计算预算或污染备份，均阻断这一恢复路径。

外部修复条件也能够使组织恢复，但事件日志明确将其标记为 `external_restore`，不计入内部提交。因此，**恢复结果相同，不意味着组织自主性相同**。

## 不足与不可推出的结论

- 不是“生命出现”的证据；也没有验证自创生或严格的组织闭合。
- 持有目标程序的完整备份，故“重建”实质是已知功能的程序重组和恢复，非真正创新。
- 内部策略和世界语义检查仍为固定代码；无法修复搜索控制器自身。
- 仅一个微型系统、少量确定性场景，没有泛化证据，也未自动识别组织边界。

## 进入 V0.3 的必要条件

将内部策略也编译为可修改图程序；让系统在无完整目标备份的情况下从规范、反馈和功能测试中生成等效候选；进行多轮损伤、干预归因和未知条件验证。只有在这些条件下，才能更有力地研究维护机制本身的再生产。
