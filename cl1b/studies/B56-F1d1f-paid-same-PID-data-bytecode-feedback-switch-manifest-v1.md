# CL-1B B56-F1d1f — prospective same-PID paid data-bytecode feedback-driven switch (v1)

**PREREGISTERED BEFORE F1d1f NATIVE CODE/RESULTS.** This is a NEW investigator-authored minimal *two-opcode data-interpreting founder*, not original F1c, not a self-generated algorithm, and not general programmable same-PID opcode creation. Its goal is to test whether online functional revision *within the same PID* can occur through ordinary paid CIL data Writes, without requiring GraphLaunch or rewriting the original native opcode graph.

## Explicitly bounded claim and exact setup

One alive PID1, one fixed native CIL source of at most 40 nodes, unchanged Rust `World::with_strict_capacity(16,180,300)`, **250 finite initial credits** per isolated world; initial **no extra processes, no resource replenishment, no privileged code interventions**. A *virtual opcode* stored in shared cell30 selects `0=IDENTITY(x)` versus `1=NEGATE(x)`. The interpreter is a prewritten branch-and-arithmetic switch implemented using ordinary CIL `Read/Branch/Sub/Write`. This is a **two-choice virtual instruction interpreter**, not a general virtual machine. Data key31 records trial stage, key20 receives a one-bit external task correctness signal, key7 carries service input, key11 records service output. Register0 is zero, register1 input/output, register2 address, register3 virtual opcode or feedback/stage.

- At first service, PID1 pays to Write virtual opcode0 to key30, stage0 to key31, Read input and virtual opcode, execute IDENTITY, Write output11. The environment reports a bit on **key20** (1 if the output satisfies the hidden task; 0 otherwise) and the held-out next input on key7. **Only these two external keys may be intervened on; external code editing, external key30/31 edits and external credits are forbidden.**
- PID1 pays to Read stage31 and feedback20; when feedback0, PID1 itself pays to Write new virtual opcode1 to key30. When feedback1, it retains virtual opcode0. It pays to Write stage1 to key31. Then the exact same PID1 executes the virtual interpreter again on the held-out input. It must not call GraphLaunch or spawn a process, and the original native CIL code graph must remain byte-for-byte unchanged. The only source of virtual-opcode change is an **actual paid Write by PID1**, not a researcher-supplied cell30 update.
- Hidden task classes: `IDENTITY` (expected output x) and `NEGATE` (expected output −x), initially x=5 or7, held-out x=11 or−7. All results are calculated from actual CIL service outputs. The selector is **preauthored**, with no algorithm generation or rich adaptation claim.

## Crossed causal controls, fixed before execution

For each initial input seed `5,7`, each hidden task `IDENTITY,NEGATE`, three feedback regimes `TRUTH,BLIND_SUCCESS,INVERTED` create exactly **12 isolated matched native worlds**, all with byte-identical founder code; no source patches between these arms. TRUTH feedback is ground-truth first-output correctness, BLIND_SUCCESS always1, INVERTED is one minus ground truth. Each world must produce two real service outputs and one PID1 feedback Read before stopping; do not judge unexecuted source as an output. Hidden held-out input is matched across arms. Fix full budget and report number of paid code instructions, actual program opcode write events, truth/feedback bit, both outputs, correctness, first-divergence replay and all strict-capacity peaks.

Preregister narrow expected outcomes: TRUTH -> correct held-out output for all four matched task/seed pairs; BLIND_SUCCESS -> wrong on both NEGATE pairs; INVERTED -> wrong held-out on all four. No expectation of outperforming preprogrammed oracle because the interpreter itself embodies the two candidates and the update rule is human-authored. The first NEGATE output is deliberately wrong; do not hide that in an aggregate headline. This isolates the causal dependence of *paid data-encoded policy selection* on service feedback; it **does not** create either candidate algorithm.
