# CL-1B B56-F1d1h — candidate-generation, native paid program evaluation and retention (prospective preregistration)

**FROZEN BEFORE F1d1h IMPLEMENTATION OR RESULT. NOT an asserted life/evolution success.**

## Dependency and unresolved bottleneck

F1d1g passed source-pinned [full CI44266492133](https://github.com/iFrankStudio/cioc/actions/runs/44266492133) with 65/65 native Rust and 56/56 independently reexecuted observers: one immutable 77-node PID1 CIL interpreter paid to change two data program slots, and actually executed the composed virtual program `[LOAD,NEGATE,ADD_LITERAL,RETURN]`. This proved **charged, same-PID bytecode composition**, not a genuinely actor-generated algorithm search. F1d1g's entire choice to write both slots on negative feedback was **preauthored** and provided no independent candidate valuation. The next experimental obstacle is therefore selection and retention between **multiple generated candidate bytecode programs**, under genuine finite costs and hidden task changes.

## Primary prospective falsifier

Can a single original PID1, without any host source edit or GraphLaunch, **pay to derive at least three different executable data-program candidates from its existing code/data**, evaluate each on at least TWO distinct probes by executing the virtual interpreter, and retain the candidate with the best locally accumulated valid feedback score for an independent held-out task input? The actor must maintain its own candidate index, candidate-slot modifications, paid evaluation records, running score and retained best program, with no privileged free replay or host source selection.

Three initial **structural candidate families** (not manually injected complete program snapshots) are permitted as a *minimum mechanical preflight*:
- A: `[LOAD_INPUT,RETURN]`, function `x`.
- B: generate from A via a PID1-paid source-data-slot edit to `[LOAD_INPUT,NEGATE_ACC,RETURN]`, function `−x`.
- C: generate from B via a further PID1-paid opcode-slot edit to `[LOAD_INPUT,NEGATE_ACC,ADD_LITERAL,RETURN]`, function `−x+2` for actor-controlled data literal2.
These are **three explicitly available authored primitive templates**, not spontaneous creation of new opcode semantics; enumeration logic must not be labeled open-ended program invention. The implementation must account for each actual mutation and ensure changing a candidate's program slot does not inherit a score from a different candidate.

## Native strict environment, experimental controls

- Unchanged `cl0-world` Rust VM; `World::with_strict_capacity(16,180,300)`; **≤180 original native source nodes, ≤16 simultaneous occupied shared cells, ≤300 total occupied units**, and a prespecified finite credit budget no greater than4000 per world. Absolutely one PID1; no GraphLaunch, external program-slot intervention, identity relabel or host fitness-target import into actor memory.
- Hidden tasks `IDENTITY, NEGATE, NEGATE_PLUS_TWO`; three candidate functions above. At least two distinct training/probe inputs per candidate and a third independent held-out input; controls must include seeds with negative and positive values and reject alias cases where two candidate programs agree on all probes. Counterbalance candidate evaluation order if it is not intrinsically necessary to the mutation grammar, or explicitly quantify order bias and random-access cost if reversing order requires a different founder. Every native instruction and environmental intervention is accounted.
- Environment provides **only input values and ordinary correctness feedback bits after real service outputs**. For correct `truth` arm, compute match with the withheld target function; for `blind success` fixed1 and `inverted` flip the bit. Include one genuinely **absent-feedback** arm separately (do not rename fixed-success feedback into absence): an omitted cell20 must yield the substrate's defined zero-on-missing Read; report this as a nontrivial default-value ambiguity, not a valid correctness bit. Test an *edit-only suppression* arm preserving the native interpreter but inhibiting paid candidate-slot revisions, and a frozen-candidate control preserving the native candidate sequence. No host-selected winner, no copying an oracle recommendation into the actor's memory.
- Score and retention logic is necessarily a **preauthored rule**, and any claimed held-out improvement must compare costs, not merely raw correctness. Score must be stored and updated by actual PID1-paid CIL instructions. A candidate can be declared `best` only based on scores accumulated from real paid executed candidate trials; report ties and tie-breaking. The retained program must be reexecuted on held-out input in the same PID1, with its real intermediate accumulator checkpoints.
- Any full native source graph exceeding strict180 nodes or simultaneous cell count exceeding strict16 **fails**; no implicit increased resources or rewritten kernel physics for success. A negative capacity result is publishable. If 180 nodes is insufficient for generic candidate search/evaluation logic, preregister a smaller or modular actor within the SAME limits before executing results; never covertly preassemble separate full candidates or add host-side program-selection.

## Verification and scientific decision

Before native source implementation, freeze a follow-on exact manifest with opcodes and addresses, candidate generation grammar, evaluator score updates, seed/feedback cohorts, event trace schema and negative-control implementation. Run native Rust source-pinned CI with an **independent dynamic event-by-event CIL replay** that reconstructs the live founder source, all paid mutations, register/PC/memory/process identity, finite credits and held-out outcomes. Flag all native traps/halts and fail on first divergence.

Accept a limited **charged same-PID generated-candidate evaluation and score-based retention** only if evidence excludes free winner selection and preassembled complete candidate loading. Do not infer autonomous origin of the primitive ISA, autonomous selection-rule discovery, open-ended instruction classes, B51c/F1c task-search continuity, authenticated B53 feedback, strict N56-A/B/C, B3/B4 or cyberlife. If every available candidate is hardcoded as a full source branch, classify the result only as authored policy selection.
