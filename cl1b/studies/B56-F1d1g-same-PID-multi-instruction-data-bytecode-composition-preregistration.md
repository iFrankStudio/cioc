# CL-1B B56-F1d1g — preregistered multi-instruction same-PID data-bytecode composition experiment

**FROZEN BEFORE ANY F1d1g NATIVE IMPLEMENTATION OR OBSERVER RESULT.** B56-F1d1f established a strict same-PID, two-choice **data-mode** feedback switch, not a general interpreter or de-novo program. Follow-up tests whether a richer, explicitly preauthored data-bytecode VM can execute a **sequence** of actor-paid-revised instructions while never changing PID, native CIL graph, or world physics.

## Independent hypothesis, null and identity constraints

H1: An existing PID1 that pays ordinary native CIL to manage an interpreted **virtual program counter and at least three separate virtual instruction slots** can update **two or more virtual instruction slots after task feedback**, and then execute a multi-instruction program whose entire composed function is not a single hardcoded complete candidate service path in its original executable source. The resulting service must arise from at least two successive actual interpreted operations (e.g. NEGATE and ADD_LITERAL) and a native charged Write11 in the **same PID1**.

H0: all measured outcomes can be attributed solely to one fixed preauthored service branch (the F1d1f two-mode limitation), external data edits, hardcoded host fitness code, code-graph replacement, or a new PID. A source-program lookup/host-crafted answer or prewritten full NEGATE_PLUS_TWO shortcut cannot reject H0. No claims of unbounded interpreter universality, autonomous discovery or novel instruction semantics even if H1 passes.

## Frozen experiment envelope and exact virtual ISA

- Unmodified Rust CL0 VM, one original PID1; `World::with_strict_capacity(16,180,300)`; bounded 1,000 paid instructions per isolated world; no pool draw, no graph launch, no external source edit, no actor credit reset.
- Use ordinary paid `Read`, `Write`, `Branch`, `Add`, `Sub` and constants to implement a **single fixed native interpreter** with a virtual PC in cell50; bytecode slots51–54; optional literal cell55; accumulator cell56. Reserved input7, output11, feedback20 and stage31. **At most 11 simultaneous data keys**; preserve all per-step occupancy evidence.
- Minimal virtual opcodes: `0=LOAD_INPUT`, `1=NEGATE_ACC`, `2=ADD_LITERAL`, `3=RETURN_WRITE11`. The interpreter must *fetch an opcode from key(51 + virtual PC)*, decode, execute the specified primitive, update the virtual PC as data, loop or return, charging genuine CIL instructions at every step. It may not simply branch on a single mode byte to complete IDENTITY vs NEGATE_PLUS_TWO in two authored code paths. Test a program with a genuine **NEGATE_ACC then ADD_LITERAL** sequence and preserve its intermediate accumulator value in the native evidence.
- Initial program before the first service `[LOAD_INPUT,RETURN,RETURN,RETURN]` (one output identity). Hidden task is `IDENTITY(x)` versus `-x+2`. After first *real* service Write11, the environment supplies a one-bit correctness signal at key20 and a held-out input7. The same PID1 reads the bit for one paid CIL instruction and, **only if false**, pays to Write slot52=NEGATE and slot53=ADD_LITERAL while retaining slot54=RETURN (including any necessary shift to ensure sequential PC0..PC3). Log exact multi-cell data-program edit provenance and distinguish immutable initial program from later paid revisions. No external updates to keys50–56 or stage31.
- Exact candidate encoding, interpreter PC semantics, negative and zero arithmetic edge cases, CIL source layout and charged Write11 count **must be fixed by a second manifest revision BEFORE native test source implementation** if unavoidable; otherwise adhere literally to these bytes. No post hoc outcome-driven adjustments.

## Matched controls

At least **2 independent input/held-out pairs**, both hidden task classes, crossed with `TRUTH`, `BLIND_SUCCESS`, `INVERTED` feedback, plus an **interpreter-edit-only suppression** using a specified control that preserves interpreter execution and all native computational costs other than the actual targeted updates; do not silently disable all native source mutations (which would be irrelevant here). Include a no-feedback baseline, optionally a static oracle labeled authored. Require actual first-service correctness, held-out functionality and full resource/credit counts, not just an expected-output label.

Pre-register nonadaptive first-service behavior as IDENTITY for all worlds; truthful adaptive revision should correctly select the `-x+2` composed program only in the shifted task cases; blind constant-success should fail in the latter cases; inverted feedback should degrade both. Do not assert practical utility improvement against a strong static oracle without actual measurements. Require a held-out input not equal to either first input and no accidental functional alias of the two candidates.

## Verification and rejection gates

Archive source SHA, frozen-manifest hash and exact original Rust PID1 paid event histories, including every virtual PC fetch, decoded opcode, register/accumulator state, multi-slot paid Write and service Write, external intervention origin, final code byte equality, credits and strict storage/compute peaks. Build an independently authored **complete** event-by-event CIL/bytecode replay, not a summary-only guessed fitness score; fail on first divergence. Include at least one negative control demonstrating removing a requested virtual-slot update prevents the composed program from executing, while maintaining PID identity and source equality.

**Success only:** source-authored general small virtual interpreter, actual same-PID paid multi-slot program revision and multi-operator composition under resource constraints. **Still NOT success:** original F1c strict source-origin, B53 authenticated feedback, autonomous discovery of virtual primitives or the adaptation rule, open-ended evolution, N56-A/B/C, B3/B4 or cyberlife. This is a new founder mechanism calibration, not retroactive success for F1d1e literal native-opcode reachability.
