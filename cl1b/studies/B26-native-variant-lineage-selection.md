# CL-1B / B26 — native-coded heritable request variation exposed to resource selection

**Prospective registration 2026-11-16, before implementation or B26 outcomes.** This study tests a new **mechanistic intermediate stage** between the preauthored, separately loaded competitors of B25 and true autonomous evolution. It must **not** be presented as spontaneous mutation discovery, successful adaptation or digital life.

## Core experiment

**One researcher-loaded CIL founder** copies *its own five-node resource-consuming/service loop* into a newly allocated native graph, performs CIL arithmetic to generate a **different request literal**, writes it into the child graph via native `GraphSetConst`, and launches that child with transferred (not minted) credits. Both parent and child then compete for **exactly the same identity-neutral external world compute pool**, and their separately attributed genuine service writes are measured.

This differs substantially from:
- **B21:** investigator loaded both actor and helper separately.
- **B22:** one actor launched a helper, but **its complete helper source algorithm was already embedded in inert template instructions**.
- **B25:** two preauthored policies competed, but both were externally loaded and no native lineage/code alteration occurred.

B26's second executable is produced **inside the world by CIL operations**, from a copy of the parent's own worker source rather than a separately supplied child-role template, and it has a CIL-computed request-literal difference. But the full copying/mutation recipe, candidate arithmetic and task remain researcher-authored. A child-request value not present as a *prewritten helper program* does not mean the mutation choice was independently discovered. Neither continued offspring production nor inheritance into a second generation is tested here.

## Frozen 35-node CIL founder

One source program, **34 initial local compute credits**, world pool0, strict world capacity (16 cells, 64 max nodes/process, 128 aggregate storage), and opt-in generic laws `with_pool_paid_draw()` plus `with_recoverable_draw_shortage()`. The host initially loads **only process1**, and never calls `SetCredits` or externally loads any additional process.

- PCs **0..10:** `GraphNew` followed by five `Const(source-index)` / `GraphCopyNodeLocal` pairs, copying original parent's own worker PCs30..34 into the new graph's nodes0..4.
- PCs **11..22:** four groups of `Const(node index)`, `Const(target index)`, `GraphSetNext` to rewire normalized forward edges 0→1→2→3→4; the local copied worker's final Write4→Draw1 is preserved.
- PCs **23..27:** compute a proposed child request using ordinary CIL arithmetic, then native `GraphSetConst` of child graph node0. The source request held at PC30 is unaffected.
- PCs **28..29:** `Const transfer amount=2`, then native `GraphLaunch` of child2, transferring two local credits. No host spawn, privileged reward or free compute grant.
- PCs **30..34:** *the only complete service program in the founder*: `Const r0=base request → DrawCompute → Const r2=9 → Const r3=1 → Write cell9=1 → DrawCompute`. The internally assembled child runs a copy of exactly this five-node worker, with only request `Const` rewritten.

The initial CIL program performs exactly30 charged graph/variant/launch attempts, transferring2 credits into the child while leaving2 for its own worker. Each consumes its two startup instructions before all available initial34 compute credits are gone. The first child must appear **after a native GraphLaunched event**. No independent helper program is host-loaded.

## Three equal-length, equal-cost authored mutation controls

All CIL actions and startup compute have the same length/cost, but investigators select these frozen alternatives:

1. **PARENT4_CHILD3:** parent's worker request4; child variation calculated in CIL by `4−1`, patched onto the copied graph via `GraphSetConst`. The child requests3.
2. **PARENT3_CHILD4:** swap policies/IDs: parent's worker request3; child variation calculated by `3+1`, same cost/graph operations. This checks whether the advantage under scarcity belongs to **request size rather than child ID / spawning position**.
3. **PARENT4_CHILD4:** control with base4 and `4−0` in the same paid CIL instructions, resulting in an *identical* child policy; GraphSetConst still runs and charges. This isolates the value of actual variation from merely creating a second consumer.

The **signed candidate mutation rules are hand-authored**. This is not an unrestricted evolutionary operator or population search.

## Environmental conditions, 12 total worlds

Same four preregistered six-packet neutral pool schedules used for B25:
- Scarce A: `[4,4,4,4,4,4]`.
- Loose B: `[5,5,5,5,5,5]`.
- Mixed C: `[4,5,4,5,4,5]`.
- Reverse mixed D: `[5,4,5,4,5,4]`.

Three founder variants × four schedules = **12 fully retained worlds**. After bootstrap and after each explicit external pool packet, run **until blocked**; retain residual pool credits and traps, no host refills, no host selection or actor targeting.

## Primary causal verification

- At t0, process2 **does not exist**. Native `Origin::Internal(1)` provenance must confirm exactly one `GraphCreated`, five `GraphNodeCopiedLocal` from parent worker source30..34, four `GraphNodeEdited(next)`, one `GraphNodeEdited(const)` at child graph node0, and one `GraphLaunched(parent1,child2,transferred_credits2,moved_nodes5)`.
- The child executable graph must actually have **five native instructions** with only initial request literal changed by the internally computed CIL mutation; all control edges and work opcodes remain the same. No original complete child template or host `PutGraph`.
- Initial source worker request4 (or3) stays unchanged. The child/parent identity assignment swap must be checked at the source literal level, not inferred solely from event counts.
- Combined local+pool compute inventory declines exactly1 per native charge and rises only from explicitly external neutral pool packets. All service writes must be real native `CellWritten(key9,value1)` with `Origin::Internal(parent/child)` and the proper PC.
- **Under scarce A**, a runnable request3 contender should receive service opportunities while request4 is excluded by the per-draw threshold, provided a request3 process is present; this effect must follow request3 after swapping parent/child IDs. The PARENT4_CHILD4 control may accumulate pool credits and must not be hand-excluded.
- Under looser B and mixed C/D, preserve any process-ID / round-robin scheduling advantages and differences caused by accumulated pool credits. Do not define success solely by which PID wins.
- No actor changes its source policy during the pool-competition phase, and there is no second-generation child in this study. The *mutation* is one CIL-generated child code edit before launch, **not adaptive search**.

## Acceptance boundary and scientific significance

An actually passing native B26 would establish **CIL-originated first-generation structural replication plus a CIL-computed, heritable-looking executable variation subject to identity-neutral differential resource access**, all under finite compute/storage accounting. This is an important **precursor** to actual digital evolution. It does **not** demonstrate mutation rates outside the designed rule, fitness-based genotype accumulation, spontaneous self-maintenance, autonomous goals, reproduction across generations or open-ended complexity. The only reliable next scientific gate is native *multi-generation*, resource-paid mutation/replication with no host-chosen winners, no complete new candidate program injected, and held-out environmental variation.
